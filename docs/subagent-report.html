觀察到的六件事

標籤標示的是性質，不是嚴重度排序——它們彼此獨立，沒有先後關係。

停滯

兩次派工吃掉將近四分之三的等待時間

第 18 號派工跑了 86 分 24 秒，只做了 13 次工具呼叫、用掉 30k token。 第 12 號做的是結構上完全相同的工作——對兩個檔案做小而明確的修改—— 45 秒完成，同樣是 13 次工具呼叫。同一個角色、同一種形狀的任務， 掛鐘時間差 116 倍。

它的產出是正確的：回報格式完整、測試通過、主 session 獨立複驗也同意。 輸出裡沒有任何東西能解釋那 86 分鐘，而工具呼叫次數排除了「它只是慢慢做了很多事」。 這看起來是執行環境的停滯，不是一個昂貴的任務。

掛鐘時間不計費，但它會卡住整條產線：主 session 在派工回來之前無法裁決、部署或提交。 第 13 號停滯期間，harness 自己也注意到了，發出一則 goal check-in 說「因為背景工作仍在執行， 評估已延後 34 分鐘」。

可操作的判準 當一次派工的掛鐘時間超過該角色中位數的約 10 倍，它不是「快好了」——去查。 不必讀子代理的 transcript（那是個大到會撐爆呼叫端 context 的 JSONL）， git status 與檔案 mtime 就能看出它到底寫過東西沒有。 第 13 號在 34 分鐘後一個檔都沒寫。
Hook

routing hook 在「派出時」就宣告「剛回來」

route plugin 的 PostToolUse:Agent hook 會送出這句：

[routing] builder just returned. Before moving on, apply the Step 4 review policy…

這段文字是附在啟動的結果上的——就是那個寫著 Async agent launched successfully 的同一個 tool result， 而且在我發出的 7 次 route:builder 派工中出現了 6 次。 因為這些代理跑在背景，Agent 工具呼叫在啟動當下就回傳了， PostToolUse 自然也就在那時觸發。builder 根本還沒回來，它才剛開始。

這則提醒本身有用，但它的措辭會誘導出錯誤動作：在那個當下去套用 Step 4 審查政策， 等於派一個 reviewer 去審一批還不存在的檔案。正確的讀法是 「你剛派出一個 builder，記得規劃審查」，而審查必須等完成通知。

scout、reviewer、scribe 的派工則不會觸發這則 hook。

停滯

被終止的代理仍會回報最後一句話，那就是診斷依據

對第 13 號執行 TaskStop 後，收到的是一則正常的 task-notification， status: killed，而 result 欄位裡是它的最後一句話：

Now I'll record the release following the size-discipline rolling rules. Let me work in the correct order: destination files first, then source files.

Step 1: Prepend oldest PROGRESS.md entry to PROGRESS_ARCHIVE.md

34 分鐘過去，還在宣告四個步驟中的第一步。就是這一行讓我判定這是停滯而非緩慢進展， 而取得它的代價是零——不像那個絕對不能讀的 .output transcript。

重試在 3 分 20 秒內完成。它的 prompt 短了大約 40%， 同樣四項編輯改用編號清單而非散文敘述。單一 session 不足以證明 prompt 長度就是停滯主因， 但把 brief 縮短是零成本的，而重試是目前唯一的資料點。

流程

builder 會把呼叫端的髒工作區當成 blocker 回報

第 10、12、16、18 號派工的回報都以一段 BLOCKERS: 收尾， 列出主 session 自己改過的檔案——版號更新、其他 builder 的產出、派工前先寫好的測試。例如：

git status shows README.md, package.json, package-lock.json, and src/version.ts already modified before I started. None of these are in my Files list; I left them untouched.

這個行為是對的——代理守住了範圍並且說明了。但它讓每份回報都以一個看起來很嚇人的標題結尾， 每次都得讀過再排除。往一個本來就有無關改動的工作區派工時，在 brief 裡先說明， 代理就會把它歸類為背景脈絡而不是阻礙。

流程

沒被告知流程規則的 reviewer 會給出誤判的 FAIL

第 11 號回傳 FAIL 與兩個 BLOCKER，形式都是「測試檔被修改但不在 builder 的 Files 清單裡」。那兩個測試檔是主 session 在派工前寫的， 這正是本專案 Lane 2 的既定流程，builder 從未碰過。 reviewer 套用了「測試檔在範圍外被改動 ⇒ 自動 FAIL」，卻不知道是誰寫的。

它在同一份回應裡的實質分析非常徹底，而且沒有找到任何缺陷，所以裁決改判為 PASS。 之後的 reviewer 派工都加上一句話說明測試由主 session 擁有，誤判就沒有再發生。

規則 reviewer 不會繼承任何關於派工協定的記憶。如果流程允許某個檔案在 builder 的範圍外被改動， 就必須明白告訴它——否則它會正確地套用一條它不該套用的規則。
回報

狀態顯示完成的代理，回報仍可能無法使用

第 8 號在 9 分 51 秒、65 次工具呼叫後以 status: completed 結束，但它的最終回報是：

Line 641 confirms it. Let's inspect context.

這不是一份完成報告，而是一句被切斷的思考。工作其實有落地：檔案都在，測試也幾乎全綠。 但那份回報既無法信任也無法解析，於是主 session 用 git status 與一次測試自行重建狀態，並發現兩條真的失敗的測試——那是回報本來就該提到的。

規則 status: completed 描述的是流程，不是答案。 一份沒有包含約定欄位（檔案清單、測試數、verify 指令）的回報，就等於沒有回報， 呼叫端必須自行驗證。而這種驗證很便宜，其實應該無條件做。

要改的六件事

  1. 把掛鐘時間當成需要監看的訊號。超過該角色中位數約 10 倍時，去查它寫了什麼檔，而不是繼續等。
  2. 把 routing hook 的「just returned」讀成「just dispatched」。審查一律等完成通知。
  3. scribe 的 brief 保持精簡並編號。這次唯一用長篇散文寫的那一份，就是停滯的那一份。
  4. 工作區若已因無關原因變髒，在派工時先講。
  5. 告訴 reviewer 哪些檔案是主 session 擁有的。
  6. 不論回報的 status 為何，都獨立驗證 builder 的宣稱。綠色的回報和綠色的測試不是同一件事。
